# First Business Pilot — Launch Playbook

מטרת המסמך: להפוך עסק ראשון מ"נרשם למערכת" ל"סידור ראשון פורסם בהצלחה" בצורה מבוקרת, מדידה וחוזרת.

## 1. תנאי כניסה לפיילוט

לפני שמתחילים עם עסק אמיתי:

- [ ] Production health תקין: `/api/health` ו-`/api/health?deep=1`.
- [ ] אין תקלה פתוחה שחוסמת הרשמה, הגשת זמינות, בניית סידור או פרסום.
- [ ] מוגדר איש קשר מנהל אחד לפחות בעסק.
- [ ] ידוע האם העסק עובד בסידור שבועי או חודשי.
- [ ] ידועים הסניפים/מחלקות והעובדים הראשונים שיוזמנו.
- [ ] מוסכם חלון קצר לפיילוט: מחזור סידור אמיתי אחד לפני הרחבה.

## 2. Onboarding של העסק

### מנהל

1. יצירת העסק והסניף הראשון.
2. בחירת תדירות סידור: שבועי / חודשי.
3. יצירת מחלקות לפי הצורך.
4. יצירת סוגי/תבניות המשמרות הרלוונטיים.
5. הזמנת קבוצת העובדים הראשונה.
6. פתיחת תקופת העבודה הראשונה.

### עובדים

כל עובד צריך להשלים לפני סגירת חלון ההגשה:

- [ ] קבלת הזמנה וכניסה ראשונה.
- [ ] בדיקת פרטי החשבון.
- [ ] הגשת זמינות למחזור הראשון.
- [ ] הוספת Time Off אם רלוונטי.
- [ ] הבנת המסלול לצפייה בסידור ובקשת החלפה.

## 3. מסלול הסידור הראשון

המסלול שהמנהל מבצע בפיילוט:

1. לוודא מי הגיש זמינות ומי עדיין חסר.
2. לפתוח את Schedule Builder.
3. לבנות טיוטה ולבדוק Conflict Detector, Coverage, ShiftPilot Score ו-Fairness.
4. להשתמש ב-Smart Draft / Fix My Schedule רק כהצעה; המנהל בודק ומאשר את השינויים.
5. לפתור חוסרים או Open Shifts לפי הצורך.
6. לבצע בדיקה אחרונה של Time Off ואילוצים קשיחים.
7. לפרסם במפורש את הסידור.
8. לוודא שעובד אחד לפחות רואה את הסידור ב"המשמרות שלי".

אין פרסום אוטומטי ואין שינוי בעל השפעה גבוהה ללא אישור מנהל.

## 4. Day-1 Launch Check

מיד אחרי פרסום הסידור הראשון:

- [ ] הסידור המפורסם תואם למה שהמנהל אישר.
- [ ] העובדים רואים את המשמרות שלהם.
- [ ] אין עובד משובץ בזמן Time Off מאושר.
- [ ] אין Conflict קריטי שלא טופל.
- [ ] Marketplace / Swap עובדים רק דרך אישורי התהליך הקיימים.
- [ ] מרכז השליטה מציג מצב אמיתי ולא נתוני placeholder.
- [ ] ערוץ התמיכה זמין וברור למנהל ולעובדים.

אם קיימת תקלה חוסמת, לא ממשיכים להרחבת הפיילוט. פועלים לפי `INCIDENT_RESPONSE.md` ו-`RUNBOOK.md`.

## 5. מדדי הפיילוט

המדד הראשי: **Time to Schedule** — הזמן מהרגע שחלון ההגשה נסגר ועד שיש סידור מוכן לפרסום.

לכל מחזור מתעדים:

| מדד | מה מודדים |
|---|---|
| Time to Schedule | דקות מסגירת ההגשה עד סידור מוכן |
| Submission Completion | כמה עובדים הגישו בזמן / סה"כ עובדים |
| Manual Fixes | כמה תיקונים ידניים המנהל עשה אחרי הטיוטה |
| Critical Conflicts | כמה חוסמים נשארו לפני פרסום |
| Change Requests | Time Off / Swap / Marketplace לאחר הפרסום |
| Support Volume | מספר פניות התמיכה במחזור |

## 6. משוב אחרי המחזור הראשון

### שאלות למנהל

1. מה היה השלב שלקח הכי הרבה זמן?
2. איפה היית צריך לחשוב או לבדוק משהו מחוץ ל-ShiftPilot?
3. האם ההמלצות היו ברורות ומועילות?
4. כמה תיקונים ידניים עשית לפני הפרסום?
5. מה הדבר האחד שחייב להשתפר לפני המחזור הבא?

### שאלות לעובדים

1. האם היה ברור איך להגיש זמינות?
2. האם היה ברור איפה רואים את הסידור?
3. האם Time Off / החלפה היו ברורים כשנזקקת להם?
4. האם קיבלת מידע בזמן הנכון?
5. מה היה מבלבל או מיותר?

## 7. Go / No-Go אחרי הפיילוט

### GO למחזור/עסק נוסף

- אין P0/P1 פתוח במסלול המרכזי.
- הסידור הראשון פורסם ללא עקיפת guardrails.
- המנהל הצליח להשלים את המסלול בלי התערבות מפתח בפעולות שגרתיות.
- העובדים הצליחו להגיש ולצפות בסידור.
- אין בעיית בידוד tenant / הרשאות / Time Off.
- יש רשימה קצרה ומדורגת של שיפורים, לא חסימה מערכתית.

### NO-GO

עוצרים הרחבה אם אחד מהבאים מתקיים:

- פרסום או שיבוץ שגוי בעל השפעה אמיתית.
- הפרת Time Off / hard constraint.
- בעיית הרשאות או בידוד נתונים.
- המנהל לא מסוגל להשלים את מחזור הסידור ללא התערבות טכנית חוזרת.
- תקלה חוזרת שמונעת מעובדים להגיש או לראות את הסידור.

## 8. סיום הפיילוט

בסוף המחזור:

1. מסכמים את המדדים והמשוב.
2. מסווגים כל בעיה: blocker / high / medium / low.
3. מתקנים blockers ו-high לפני הרחבה.
4. מחליטים GO / NO-GO למחזור הבא.
5. רק לאחר GO מוסיפים עובדים/מחלקות או עסק נוסף.
