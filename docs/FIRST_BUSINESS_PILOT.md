# First Business Pilot — Launch Playbook

מטרת המסמך: להפוך עסק ראשון מ"נרשם למערכת" ל"סידור ראשון פורסם בהצלחה" בצורה מבוקרת, מדידה וחוזרת.

> בתוך המוצר: מנהלים יכולים לעקוב אחרי ההתקדמות במסך `/workspace/pilot-launch`. המסך הוא read-only ומחשב את הסטטוס לפי נתוני ShiftPilot בפועל.

## 1. תנאי כניסה לפיילוט

לפני שמתחילים עם עסק אמיתי:

- [ ] Production health תקין: `/api/health` ו-`/api/health?deep=1`.
- [ ] אין תקלה פתוחה שחוסמת הרשמה, הגשת זמינות, בניית סידור או פרסום.
- [ ] מוגדר איש קשר מנהל אחד לפחות בעסק.
- [ ] ידוע האם העסק עובד בסידור שבועי או חודשי.
- [ ] ידועים הסניפים/מחלקות והעובדים הראשונים שיוזמנו.
- [ ] מוסכם חלון קצר לפיילוט: מחזור סידור אמיתי אחד לפני הרחבה.
- [ ] העסק מסומן `pilot_mode = true` (עמודה ב-`organizations`, מוגדרת ידנית ב-SQL על ידי הצוות, לא self-serve) כדי שהוא יראה רק את הליבה — הגשת זמינות → בניית סידור → בדיקה בסיסית → פרסום → החלפה — ולא את שכבת ה-Intelligence/WOW.
- [ ] נאספה מדידת Baseline "לפני" מהמנהל דרך `/workspace/pilot-baseline` — לפני שהעובד הראשון נכנס למערכת.

## 2. Onboarding של העסק

### מנהל

1. יצירת העסק והסניף הראשון.
2. בחירת תדירות סידור: שבועי / חודשי.
3. יצירת מחלקות לפי הצורך.
4. יצירת סוגי/תבניות המשמרות הרלוונטיים.
5. הזמנת קבוצת העובדים הראשונה.
6. פתיחת תקופת העבודה הראשונה.

### עובדים

כל עובד צריך להשלים לפני סגירת חלון ההגשה:

- [ ] קבלת הזמנה וכניסה ראשונה.
- [ ] בדיקת פרטי החשבון.
- [ ] הגשת זמינות למחזור הראשון.
- [ ] הוספת Time Off אם רלוונטי.
- [ ] הבנת המסלול לצפייה בסידור ובקשת החלפה.

## 3. מסלול הסידור הראשון (Pilot Mode)

בעסק שמסומן `pilot_mode`, ה-Schedule Builder מציג רק את הליבה. ShiftPilot Score, Fairness, Smart Draft, Fix My Schedule, Smart Replacement ו-Shift Marketplace מוסתרים — לא נמחקים — עד שמחזור 1 נסגר. המסלול שהמנהל מבצע בפיילוט:

1. לוודא מי הגיש זמינות ומי עדיין חסר.
2. לפתוח את Schedule Builder.
3. לבנות טיוטה ולבדוק Conflict Detector ו-Coverage (הבדיקה הבסיסית שנשארת גלויה תמיד).
4. לפתור חוסרים ידנית לפי הצורך (Marketplace סגור בשלב זה).
5. לבצע בדיקה אחרונה של Time Off ואילוצים קשיחים.
6. לפרסם במפורש את הסידור.
7. לוודא שעובד אחד לפחות רואה את הסידור ב"המשמרות שלי".

אין פרסום אוטומטי ואין שינוי בעל השפעה גבוהה ללא אישור מנהל. רק אחרי שמחזור 1 נסגר (ראו סעיף 5) שוקלים לפתוח בהדרגה כלי Intelligence בודדים, לפי כאב שהמנהל כבר הביע — לא את כולם בבת אחת.

**חשוב:** `pilot_mode` לא רק מסתיר UI. פתיחת משמרת ל-Marketplace ובקשת/אישור משמרת פתוחה חסומות גם בשכבת ה-RPC (Postgres) לעסק שמסומן `pilot_mode`, כך שגישה ישירה ל-API (לא רק דרך המסך) נכשלת עם שגיאה ברורה במקום לעקוף את ההגבלה. Smart Draft / Fix My Schedule / Smart Replacement לא זקוקים לחסימה מקבילה — הם כותבים דרך אותה פעולת שיבוץ ידנית שנשארת חלק מהליבה.

## 4. Day-1 Launch Check

מיד אחרי פרסום הסידור הראשון:

- [ ] הסידור המפורסם תואם למה שהמנהל אישר.
- [ ] העובדים רואים את המשמרות שלהם.
- [ ] אין עובד משובץ בזמן Time Off מאושר.
- [ ] אין Conflict קריטי שלא טופל.
- [ ] Marketplace / Swap עובדים רק דרך אישורי התהליך הקיימים.
- [ ] מרכז השליטה מציג מצב אמיתי ולא נתוני placeholder.
- [ ] ערוץ התמיכה זמין וברור למנהל ולעובדים.

אם קיימת תקלה חוסמת, לא ממשיכים להרחבת הפיילוט. פועלים לפי `INCIDENT_RESPONSE.md` ו-`RUNBOOK.md`.

## 5. מדדי הפיילוט ו-Baseline

**Time to Schedule** (הזמן מסגירת חלון ההגשה ועד פרסום בפועל) הוא מדד תפעולי שימושי, אבל הוא לא מספיק כדי להוכיח ROI — הוא לא אומר כמה זמן זה לקח *לפני* ShiftPilot.

לכן, לפני שהעובד הראשון נכנס למערכת, המנהל עונה על שלוש שאלות Baseline דרך `/workspace/pilot-baseline` (שלב "לפני"):

1. כמה זמן לוקח היום להכין ולסגור סידור — כולל איסוף זמינות, הודעות, תיקונים והחלפות?
2. בערך כמה הודעות/שיחות/תיקונים נדרשים בכל מחזור?
3. מה החלק שהכי מעצבן או מבזבז זמן בתהליך הנוכחי?

מיד אחרי פרסום הסידור הראשון, אותו מנהל עונה על אותן שלוש שאלות בשלב "אחרי", ועל שאלה רביעית שבודקת עלות נסתרת:

4. האם היה משהו ב-ShiftPilot שגרם לבזבז זמן שלא היה קיים קודם (למידת ממשק, חוסר ודאות, בדיקות כפולות)?

התשובות נשמרות כפניות במרכז התמיכה (subject `[Pilot Baseline - Before]` / `[Pilot Baseline - After]`), כדי שאפשר יהיה להשוות "לפני" מול "אחרי" ולקבל מספר שיווקי אמיתי — למשל "4:00 → 1:25 שעות למחזור" — ולא רק "יש לנו AI scheduling".

מרכז השקת הפיילוט מציג בזמן אמת:
- התקדמות באבני הדרך להשקה.
- אחוז השלמת הגשות זמינות.
- אחוז כיסוי השיבוצים במחזור הפעיל.
- Time to Schedule כשהמערכת מכירה גם את `submission_closes_at` וגם את `published_at`.
- מספר משובי הפיילוט שנשמרו דרך מרכז התמיכה.

לכל מחזור מתעדים בנוסף:

| מדד | מה מודדים |
|---|---|
| Time to Schedule | דקות מסגירת ההגשה עד פרסום הסידור |
| Submission Completion | כמה עובדים הגישו בזמן / סה"כ עובדים |
| Manual Fixes | כמה תיקונים ידניים המנהל עשה אחרי הטיוטה |
| Critical Conflicts | כמה חוסמים נשארו לפני פרסום |
| Change Requests | Time Off / Swap / Marketplace לאחר הפרסום |
| Support Volume | מספר פניות התמיכה במחזור |

### מחזור 1 נחשב גמור רק כש-

1. הסידור פורסם **בלי** שהמנהל חזר ל-Excel/WhatsApp בשביל שום חלק מהתהליך, וגם
2. נאספה מדידת "אחרי" ב-`/workspace/pilot-baseline`.

`/workspace/pilot-launch` עוקב אחרי שני התנאים בפועל (לא לפי הצהרה) ומציג "מחזור 1 נסגר" רק כששניהם מתקיימים. עד אז לא פותחים כלי Intelligence נוספים ולא מוסיפים עסק שני — גם אם הסידור כבר פורסם.

## 6. משוב אחרי המחזור הראשון

המשוב נאסף דרך `/workspace/pilot-feedback` ונשמר במרכז התמיכה תחת subject שמתחיל ב-`[Pilot Feedback]`, כך שאפשר לעקוב אחר הטיפול בלי להקים מערכת משוב נפרדת.

### שאלות למנהל

1. מה היה השלב שלקח הכי הרבה זמן?
2. איפה היית צריך לחשוב או לבדוק משהו מחוץ ל-ShiftPilot?
3. האם ההמלצות היו ברורות ומועילות?
4. כמה תיקונים ידניים עשית לפני הפרסום?
5. מה הדבר האחד שחייב להשתפר לפני המחזור הבא?

### שאלות לעובדים

1. האם היה ברור איך להגיש זמינות?
2. האם היה ברור איפה רואים את הסידור?
3. האם Time Off / החלפה היו ברורים כשנזקקת להם?
4. האם קיבלת מידע בזמן הנכון?
5. מה היה מבלבל או מיותר?

## 7. Go / No-Go אחרי הפיילוט

### GO למחזור/עסק נוסף

- אין P0/P1 פתוח במסלול המרכזי.
- הסידור הראשון פורסם ללא עקיפת guardrails.
- המנהל הצליח להשלים את המסלול בלי התערבות מפתח בפעולות שגרתיות.
- העובדים הצליחו להגיש ולצפות בסידור.
- אין בעיית בידוד tenant / הרשאות / Time Off.
- יש רשימה קצרה ומדורגת של שיפורים, לא חסימה מערכתית.

### NO-GO

עוצרים הרחבה אם אחד מהבאים מתקיים:

- פרסום או שיבוץ שגוי בעל השפעה אמיתית.
- הפרת Time Off / hard constraint.
- בעיית הרשאות או בידוד נתונים.
- המנהל לא מסוגל להשלים את מחזור הסידור ללא התערבות טכנית חוזרת.
- תקלה חוזרת שמונעת מעובדים להגיש או לראות את הסידור.

## 8. סיום הפיילוט

בסוף המחזור:

1. מסכמים את המדדים והמשוב.
2. מסווגים כל בעיה: blocker / high / medium / low.
3. מתקנים blockers ו-high לפני הרחבה.
4. מחליטים GO / NO-GO למחזור הבא.
5. רק לאחר GO מוסיפים עובדים/מחלקות או עסק נוסף.

## 9. Pilot Support Operations

בפיילוט הראשון אין ערוץ תמיכה נפרד מחוץ למערכת — כל תקלה או משוב נכנסים ל-`/workspace/support`, כדי לשמור היסטוריה, סטטוס ובעלות טיפול במקום אחד.

### רמות טיפול

- **Blocker / Urgent** — אי אפשר להגיש זמינות, לבנות/לפרסם סידור, בעיית הרשאות/tenant או חשש ל-Time Off שגוי. מפסיקים את מסלול הפיילוט ומטפלים לפני המשך.
- **High** — המסלול עובד אבל דורש workaround משמעותי או גורם לסיכון תפעולי. מטפלים לפני המחזור הבא.
- **Normal** — חוסר בהירות, UX, בקשת שיפור או שאלה שאינה חוסמת. מתעדים ומעדיפים לפי ההשפעה בפועל.

### בעלות ו-escalation

1. כל פנייה מקבלת סטטוס במרכז התמיכה.
2. פנייה חוסמת מסומנת `urgent` ומועברת מיד לנתיב incident לפי `INCIDENT_RESPONSE.md`.
3. אם התקלה קשורה לפריסה/בריאות Production, בודקים `RUNBOOK.md` לפני שינוי נתונים או deploy נוסף.
4. אם יש חשש להרשאות, בידוד tenant או שיבוץ בזמן Time Off — לא מבצעים workaround ידני במסד; עוצרים ומתקנים דרך קוד/PR מסודר.
5. לפני GO למחזור הבא, אין פניות Blocker/High פתוחות שקשורות למסלול המרכזי.

### סגירת פנייה

פנייה נחשבת סגורה רק אחרי שיש `resolution_note` ברור ללקוח, והפתרון אומת במסלול שבו התקלה הופיעה. משוב מוצר יכול להיסגר גם בהחלטה מתועדת לא לבצע כרגע, כל עוד הסיבה ברורה ואינה מסתירה blocker.
