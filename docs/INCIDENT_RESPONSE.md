# תגובה לאירוע אבטחה — Incident Response Plan

מסמך זה הוא תוכנית התגובה הפורמלית לאירוע אבטחה או זמינות — מי מחליט, באיזו חומרה, ומה סדר הפעולות המדויק לבידוד, סיבוב מפתחות ושחזור. זה שונה מ-[RUNBOOK.md](./RUNBOOK.md), שמרכז נהלי תקלה טכניים נקודתיים (deploy שבור, שגיאת RLS וכו') — המסמך הזה הוא המסגרת שקובעת *מתי* כל אחד מהם רלוונטי ומי מפעיל אותו.

## חומרת אירועים ובעל ההחלטה

| רמה | הגדרה | דוגמה ב-ShiftPilot | זמן תגובה יעד |
|---|---|---|---|
| **Sev1 — קריטי** | דליפת נתונים חוצת-ארגונים (עסק א׳ רואה נתוני עסק ב׳), secret אמיתי נחשף בפומבי (repo/לוג ציבורי), או אובדן גישה מוחלט למסד הנתונים | RLS policy שנשברה ומאפשרת קריאה חוצת-`organization_id`; `service_role` key ב-commit גלוי | מיידי (דקות) |
| **Sev2 — חמור** | האתר או האפליקציה למטה לגמרי עבור כל המשתמשים | Vercel deployment שבור שממנו לא ניתן לחזור אחורה; Supabase project מושהה/לא זמין | תוך שעה |
| **Sev3 — בינוני** | פגיעה חלקית — פיצ׳ר ספציפי שבור, מיילים מתעכבים, ביצועים איטיים | תור המיילים תקוע; ייצוא PDF/CSV נכשל | תוך יום עבודה |
| **Sev4 — קל** | באג לא-חוסם, לא משפיע על אבטחה או זמינות | טעות ניסוח, יישור CSS | לפי סדר עדיפויות רגיל |

**בעל ההחלטה:** בשאר שרור — מייסד יחיד כרגע, אחראי ומחליט לכל רמות החומרה. כשיצטרפו עובדים/שותפים למערכת, יש לעדכן טבלה זו עם מטריצת אחריות אמיתית (מי מוסמך לבודד/לסבב מפתחות/לתקשר עם לקוחות).

## נוהל בעת אירוע Sev1 / Sev2

### שלב 1 — בידוד (Isolation)

- **חשד לגישה פעילה בלתי-מורשית למסד הנתונים:** Supabase Dashboard → Settings → General → **Pause Project**. עוצר גישה מיידית לחלוטין (כולל משתמשים לגיטימיים) — שקלול מכוון: עדיף downtime מוחלט זמני על פני דליפת נתונים מתמשכת.
- **חשד ל-RLS policy שבורה שחושפת נתונים חוצי-ארגון:** לזהות את הטבלה/המדיניות (`pg_policies`), ואם אין תיקון מיידי מוכן ל-deploy — לשקול `revoke` זמני של ההרשאה הבעייתית מ-`authenticated` ישירות ב-SQL, כגישור עד לתיקון אמיתי דרך migration.
- **חשד ל-secret שנחשף:** אין צורך לעצור את הפרויקט לשם כך — לעבור ישר לשלב 2.

### שלב 2 — סיבוב מפתחות (Key Rotation)

רשימת כל הסודות הפעילים במערכת, לפי סדר עדיפות לסיבוב:

1. **Supabase `service_role` key** — Dashboard → Settings → API → Generate new secret. לעדכן מיד בכל 3 המקומות: Vercel (Production + Preview + Development), GitHub Actions secret `SUPABASE_SECRET_KEY` (משמש גם ב-`database-backup.yml` וגם ב-`seed-demo-environment.mjs` המקומי).
2. **`CRON_SECRET`** (מגן על ה-worker של תור המיילים) — לגנרט ערך אקראי חדש, לעדכן ב-Vercel וב-GitHub Actions secrets.
3. **Resend API key** (שליחת מיילים) — Resend Dashboard → API Keys → Revoke הישן + Create חדש → לעדכן ב-Vercel.
4. **age keypair** (הצפנת גיבויים) — אם המפתח הפרטי נחשף: אי אפשר "לסבב" גיבויים שכבר הוצפנו עם המפתח הישן (זו בדיוק הנקודה בהצפנה אסימטרית), אבל צריך לגנרט keypair חדש מיידית, לעדכן את `BACKUP_AGE_PUBLIC_KEY` ב-`.github/workflows/database-backup.yml`, ולוודא שהמפתח הפרטי החדש נשמר אך ורק אצל בשאר (לא ב-repo, לא ב-secrets).
5. **GitHub PAT / Vercel deployment token** (אם נוצר אחד בעתיד) — לסבב דרך הממשק המתאים.

### שלב 3 — שחזור (Recovery)

- **אובדן/שיבוש נתונים:** שימוש בגיבוי המוצפן האחרון לפי הנוהל המתועד ב-[RUNBOOK.md § גיבוי ושחזור](./RUNBOOK.md#גיבוי-ושחזור) — שחזור לסביבה נפרדת (לא production), אימות ידני של הנתונים, ורק אז שחזור מבוקר לפרודקשן.
- **Deploy שבור:** נוהל "Deploy גרוע ב-Production" הקיים ב-RUNBOOK.md (Vercel Promote to last-good + `git revert` דרך PR).
- **בכל מקרה:** לתעד מה נעשה, מתי, ועל ידי מי — בלי לכלול ערכי secret בפועל בתיעוד עצמו (רק את זה שסובב, לא את הערך).

## תקשורת

כרגע (לפני לקוח משלם ראשון): אין קהל לקוחות שדורש הודעה פורמלית. ברגע שיש פיילוט או לקוח משלם אמיתי במערכת: להוסיף כאן תבנית הודעת אירוע, ערוץ יצירת קשר (מייל/וואטסאפ), וזמן תגובה מובטח — כחלק מהחוזה/SLA.

## תרגיל Tabletop

מטרת התרגיל: לוודא שבעל ההחלטה (בשאר) יודע *בפועל*, לא רק בתיאוריה, מה לעשות תחת לחץ — לא לבדוק את איכות המסמך הזה.

**תרחיש מוצע לתרגול (טרם בוצע):** "אתה מקבל התראה אוטומטית ב-03:00 שמשתמש מעסק X הצליח לראות סידור עבודה של עסק Y דרך `/workspace/schedule`. אין לך גישה למחשב הנייד, רק לטלפון." לעבור בפועל על שלבי 1–3 למעלה מהטלפון (מה נגיש מ-Supabase/Vercel mobile app, מה דורש מחשב, איפה שמור המפתח הפרטי של הגיבויים) ולתעד כאן את הפערים שהתגלו.

**סטטוס:** טרם בוצע. זו הפעולה היחידה בדף הזה שדורשת זמן אמיתי של בשאר (לא ניתן להשלים אותה מהצד שלי) — מומלץ לתאם 15 דקות ולהריץ אותה בפועל, ואז לעדכן את הסעיף הזה עם הממצאים.
